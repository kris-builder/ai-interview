# 复盘架构与技术设计

当前工作树使用 Java 17、Spring Boot、Spring AI、MyBatis-Plus、MySQL 和 Redis。页面用原生 HTML、CSS 和 JavaScript，问答支持 SSE。MySQL 保存业务数据，Redis 做请求限流。以下描述区分已知实现与各阶段目标，实际交付状态看[任务清单](../README.md)。

## 模块边界

| 模块 | 职责 | 数据归属 |
| --- | --- | --- |
| 账号与面试会话 | 校验登录与资源归属，维护面试轮次、问答及结束状态 | 本人会话、原题和原答。开场保存简历快照。 |
| 我的简历 | 保存本人多份简历，按需生成建议，按简历回看 | 个人简历与最近一次有效建议。 |
| 整场总结 | 从已结束会话中提取薄弱点、原答引用和轮次 | 一场面试一份总结。 |
| 单轮复盘 | 围绕当前原题和原答给点评、遗漏与参考答案，匹配适合的专项题 | 当前点评在请求时生成并返回。第 3 阶段增加可回看的复盘记录。 |
| 分类题库与专项题 | 供用户浏览静态参考资料，提供人工核对的专项题与评分点 | 分类资料来自仓库内材料，专项题存 MySQL。 |
| 专项复练 | 按原答找题，接受复练提交，并保存原答与新答的对照 | 题目绑定及复练提交以原答消息 ID 关联。 |

请求从页面经 Controller 到业务模块，再由 Mapper 读写 MySQL。归属来自认证账号，模型只处理通过业务校验的输入。模型调用在事务外，生成资格、保存及状态变更按业务使用短事务。

## 阶段一：总结到复练

**要解决的问题**是薄弱点已经在总结中，用户还需要自己去找正确轮次和练习。

1. 用总结里的轮次定位本人场次的原答，沿用现有的单轮复盘入口。
2. 已有复练对照时直接读取。有合适专项题时可进入练习。无匹配时仍能回到原答，并在分类资料存在时继续复习。
3. 打开总结时无需给每轮发起模型请求。这个阶段可复用现有接口和表。

**验收**用两个不同薄弱点验证定位。用库存题完成「原答 → 变式 → 对照」，再刷新回看。覆盖无匹配、未作答和历史总结。 [任务 #2](https://github.com/kris-builder/ai-interview/issues/2)

## 阶段二：按各自题意对照

**要解决的问题**是现有对照提供专项题题干和两次回答，原题条件可能无法从原答本身还原。

1. 以同一已授权场次的轮次读取原题和原答，再读取当前专项题及其评分点。
2. 模型同时看到两道题各自的条件和两次回答。按同一个知识点比较，接受正确的等效实现。业务模块校验评分点与引用是否对应。
3. 失败时沿用现有重试路径，保留最近一次成功对照。此阶段优先复用现有表和复练提交入口。

**验收**先人工确定「只说加锁」「答清原子性但遗漏库存不足」「两步都答清」「错误回答被逐字引用」的预期，再加入等效解法和题干条件不同两种变式。固定模型输出用于验证引用和失败处理，真实模型样例用于验证技术判断。 [任务 #3](https://github.com/kris-builder/ai-interview/issues/3)

## 阶段三：稳定回看

**要解决的问题**是同一轮复盘目前会重新生成点评，已绑定的题却能继续存在，两者可能失配。

1. 以原答消息为关联，保存一份有效点评、遗漏、参考答案和对应的推荐。无匹配时也能保存点评。原有练习及对照可继续读取。
2. 同一原答的请求在调用模型前取得生成资格。模型运行在事务外，成功后提交结果，失败可重试。读到已保存结果时直接返回。
3. 数据库更新随该阶段交付。新库沿用单文件初始化方式，已有库提供单独升级路径。具体表结构在实施时结合已有数据确定。

**验收**覆盖刷新回看、两个标签页提交同一轮、生成失败重试、无题的历史点评、旧练习以及另一账号访问。技术验收和真实模型验收分别记录。 [任务 #4](https://github.com/kris-builder/ai-interview/issues/4)
